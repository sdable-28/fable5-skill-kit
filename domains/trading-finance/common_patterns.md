# Trading & Finance — Common Task Patterns

## 1. Validating a new backtest result before believing it
**Trigger:** Any backtest run claims an edge, improvement, or new equity high — especially one that beats baseline by >10%.
**Approach:** 1. Confirm the exact commit, config flags, and data range the run used. 2. Split results in-sample vs out-of-sample halves; require both halves positive independently. 3. Check trade count — under ~100 trades, treat WR and expectancy as noise. 4. Hunt look-ahead bias: any indicator using bar N's close to decide entry AT bar N's open, any `tail(n)` on a full dataset, any level computed from data not yet available at signal time. 5. Re-run with realistic fills (next-bar open or worse, spread + slippage per instrument) and compare to idealized fills. 6. Compare per-month P&L to baseline month by month — a single outlier month carrying the total is regime luck, not edge.
**Checklist:** `[ ] commit+config recorded [ ] H1/H2 both positive [ ] N ≥ 100 trades [ ] no look-ahead in entry/exit path [ ] fill model degraded, edge survives [ ] no single month > 50% of net [ ] max DD and recovery time recorded`
**Variation:** The edge survives every check but was found by iterating parameters against the SAME test set — that is curve-fitting by search. Log every falsified variant; if 10 variants died before this one, discount it accordingly.

## 2. Diagnosing a live-vs-backtest divergence
**Trigger:** Live fills, P&L, or signal firing differ from what the backtest predicted for the same session.
**Approach:** 1. Pull the live log and the backtest trace for the same session, bar by bar. 2. Diff signal timestamps first — a signal firing 1 bar late means data-feed timing or aggregation mismatch, not strategy logic. 3. Diff entry prices: backtest fill at signal-bar close vs live fill at next tick = structural slippage; quantify it in points per trade. 4. Check state divergence: session accumulators (cum P&L, loss counters, position-sizing tier) that reset on live restart but persist in backtest. 5. Check contract/symbol mismatch (rollover, front-month vs continuous). 6. Only after all data/execution causes are excluded, suspect strategy code paths that branch on live-only inputs.
**Template:** `Session: ___ | Signals bt/live: ___/___ | First divergence bar: ___ | Cause class: [feed timing | fill price | state reset | symbol | logic] | Pts lost to divergence: ___ | Fix + parity re-verify date: ___`
**Variation:** Blaming "slippage" for what is actually a state-persistence bug (restart reset a sizing ladder or daily-loss counter). Slippage is bounded and symmetric-ish; state bugs compound and skew one direction.

## 3. Sizing a position under prop-firm trailing drawdown
**Trigger:** New trade signal, new account, or any change to stop distance, contract cap, or account equity vs trailing floor.
**Approach:** 1. Compute available drawdown = current balance − trailing floor (check whether floor is EOD-trailing or intratrade, and whether it locks). 2. Set daily loss cap at ≤75% of available DD near the floor. 3. Per-trade risk = min(fixed dollar cap, daily cap ÷ 2) so two losses never breach the day. 4. Contracts = floor(per-trade risk ÷ (stop points × point value)); if 0, skip the trade — never widen risk to force a fill. 5. After any stop widening, recompute contracts before submission. 6. Re-derive the whole ladder after every realized P&L change, not once per day.
**Checklist:** `[ ] floor type verified (EOD vs intratrade, lock rule) [ ] available DD computed from today's floor [ ] 2-loss survival at daily cap [ ] contracts recomputed after stop change [ ] consistency rule (max-day %) checked before pressing size`
**Variation:** Sizing off starting balance instead of the trailing floor — the floor rises with equity on trailing accounts, so yesterday's safe size breaches today. Recompute from the floor, never from a cached number.

## 4. Post-mortem on a losing streak / drawdown cluster
**Trigger:** 3+ consecutive losses, a daily cap hit, or drawdown exceeding 2× historical average.
**Approach:** 1. Pull every trade in the cluster: signal type, direction, session context, MAE/MFE. 2. Classify each loss: bad fill, bad stop placement, valid setup that failed (variance), or setup firing in the wrong regime. 3. Check correlation — multiple strategies losing the same direction same day means one bias expressed through many signals, not independent bets. 4. Compare cluster conditions (trend regime, volatility, session type) against the conditions the edge was validated in. 5. Decide: variance (change nothing), regime mismatch (add a gate, then re-validate full-period), or defect (fix, then re-run baseline). 6. Look for what was MISSING (a signal that should have fired the other way), not just what to block.
**Template:** `Cluster: ___ trades, ___ pts, dates ___ | Variance/Regime/Defect: ___ | Shared direction? Y/N | Regime at loss vs validation regime: ___ | Action: [none | gate + full re-validation | code fix + baseline re-run]`
**Variation:** Reflexively adding a blocking filter per losing pattern. Each calendar-shaped or condition-shaped block overfits to the cluster; require the block to improve BOTH out-of-sample halves or discard it.

## 5. Deploying a strategy change to live execution
**Trigger:** Any edit touching signal emission, order routing, position management, or account state on a live system.
**Approach:** 1. Write a variable-by-variable execution trace BEFORE committing: signal → sizing → order submit → fill → stop placement → trail → flat, naming every field's value at each step. 2. Verify the change in backtest reproduces the prior baseline exactly where behavior should be unchanged (confirming run, to the dollar). 3. Deploy outside market hours; confirm the process restart correctly reloads persisted state (cum P&L, ladders, open-position recovery). 4. Watch the first live session's log in real time; compare each fired/blocked signal against expected behavior. 5. Keep the rollback commit hash written down before deploying.
**Checklist:** `[ ] execution trace written [ ] confirming backtest matches baseline to the dollar [ ] deploy window is flat/overnight [ ] state reload verified after restart [ ] first-session log watched live [ ] rollback hash recorded`
**Variation:** "Refactor-only" changes that alter float rounding, iteration order, or default args and silently shift fills. If the confirming backtest differs by even one trade, the change is NOT behavior-neutral — diff the trade lists before shipping.

## 6. Rolling a futures contract / handling symbol transitions
**Trigger:** Front-month expiry approaching (volume migrating to next contract), or price/level discontinuities appearing in stored data.
**Approach:** 1. Confirm roll date by volume crossover, not calendar expiry. 2. Switch the live symbol via config/env override, never hardcode. 3. Keep old-contract bars in a separate store — do not overwrite or upsert new-contract bars into the old series; the price gap corrupts every level and indicator computed across the seam. 4. Recompute reference levels (prior-day H/L, session levels, S/R) from new-contract data only. 5. Verify first post-roll session: quoted price matches broker platform, levels are sane, position sizing unchanged.
**Checklist:** `[ ] volume crossover confirmed [ ] symbol via override [ ] separate storage, no cross-contract upsert [ ] levels recomputed on new contract [ ] first-session price/level sanity check`
**Variation:** Backtesting across the roll on a naively stitched series — the roll gap prints as a phantom 50–100pt move that triggers gap logic, breaks ATR, and fabricates or destroys trades at the seam. Use back-adjusted data or exclude seam sessions.
