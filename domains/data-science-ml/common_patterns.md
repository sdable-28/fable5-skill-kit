# Common Patterns — Data Science & AI/ML Engineering

## 1. Hunting label leakage in a suspiciously good model
**Trigger:** Validation metric jumps far above baseline (AUC > 0.95 on a hard problem), or offline wins evaporate in production. Treat "too good" as a bug report, not a win.
**Approach:** 1. Rank features by importance (SHAP or permutation). 2. For each top-5 feature, write down when its value becomes known relative to prediction time. 3. Rebuild the top feature as-of prediction time only; if the metric collapses, leakage confirmed. 4. Audit the join keys — post-outcome tables joined without timestamp filters are the usual carrier. 5. Re-split: verify no entity (user, account, session) appears in both train and test. 6. Retrain with the point-in-time features and report the honest number.
**Checklist:** [ ] Every feature timestamped and available before prediction time [ ] Splits are temporal for time-ordered data, grouped by entity otherwise [ ] Target not derivable from any feature (correlation of each feature with label < suspicious threshold) [ ] Imputation/scaling fit on train only [ ] No post-outcome tables in the join graph.
**Variation:** Partial leakage — the feature is legitimate 95% of the time but leaks for one segment (e.g., "days_since_last_contact" backfilled after churn). Check leakage per segment, not just globally.

## 2. Standing up a baseline before any modeling
**Trigger:** New prediction problem lands; anyone proposes an architecture before a baseline exists.
**Approach:** 1. Define the prediction target, prediction time, and the business metric in one sentence each — get sign-off. 2. Ship the dumbest predictor: majority class, last value, or mean by group. 3. Ship one rules/heuristic baseline using domain knowledge. 4. Ship logistic regression or gradient-boosted trees on raw available features. 5. Record all three on the same temporal split. 6. Any proposed model must beat #3 on the business metric to justify its complexity; if #2 (rules) is within noise of #3, recommend rules, not ML.
**Template:** `Target: ___ | Predict at: ___ | Business metric: ___ | ML metric: ___ | Split: train ≤ ___, val ___–___, test > ___ | Majority/last-value: ___ | Rules: ___ | GBT: ___ | Bar to beat: ___`
**Variation:** Baseline skipped "temporarily" then never revisited — the neural net's +0.02 AUC over nothing is celebrated with no evidence it beats a 20-line heuristic.

## 3. Diagnosing silent model degradation in production
**Trigger:** Business metric drifts down while model dashboards look green, or labels arrive too late to compute live accuracy.
**Approach:** 1. Compare live feature distributions to training distributions — PSI per feature (alert at PSI > 0.2), ADWIN on streams. 2. Compare live prediction distribution (mean score, score histogram) to the validation set's. 3. Check upstream: schema changes, null-rate spikes, unit changes, a feature silently defaulting to its imputation value. 4. Backfill labels for the most recent labeled window; compute metric on it. 5. Classify: feature drift (inputs moved) vs concept drift (input→label relationship moved). 6. Feature drift with intact concept → retrain on recent data; concept drift → re-examine framing and features; broken pipeline → fix upstream, no retrain.
**Checklist:** [ ] PSI per feature vs train [ ] Prediction score distribution vs val [ ] Null/default-value rates per feature [ ] Upstream schema diff [ ] Delayed-label metric on newest labeled window [ ] Retrain trigger documented (threshold, cadence, owner).
**Variation:** The imputation mask — an upstream outage makes a feature null, imputation fills it with the training mean, distributions look plausible, and the model quietly predicts the prior for weeks. Monitor null rates separately from value distributions.

## 4. Selecting the evaluation metric for an imbalanced classifier
**Trigger:** Positive class < 10%; stakeholder asks for "accuracy"; or precision/recall trade-off is undecided.
**Approach:** 1. Get the cost asymmetry in dollars or hours: cost of a false positive vs a false negative. 2. Reject accuracy outright at this imbalance. 3. Use PR-AUC, not ROC-AUC, as the offline model-comparison metric (ROC-AUC flatters at high imbalance). 4. Pick the operating threshold from the cost ratio on the validation PR curve — never default to 0.5. 5. Check calibration (reliability curve, Brier score) if scores feed downstream decisions or ranking. 6. Report the confusion matrix at the chosen threshold translated into business units ("37 fraud cases missed/month"), and state the metric the model must NOT degrade.
**Template:** `Positive rate: ___% | FP cost: $___ | FN cost: $___ | Comparison metric: PR-AUC | Threshold: ___ chosen by ___ | Calibrated: Y/N (method: ___) | Guardrail metric: ___ | Business translation: ___ per ___`
**Variation:** Metric gaming — the team optimizes recall@threshold and hits it by flooding predictions, silently destroying precision. Always pair the target metric with a guardrail metric that must not regress.

## 5. Fine-tune vs prompt vs RAG decision for an LLM feature
**Trigger:** Someone proposes fine-tuning; or a prompted LLM feature hallucinates or misses domain knowledge.
**Approach:** 1. Classify the gap: missing *knowledge* (facts the model can't know) vs missing *behavior* (format, tone, task procedure). 2. Knowledge gap → RAG: chunk sources (start ~300–800 tokens with overlap, respect document structure), embed, retrieve top-k, cite. Never fine-tune to inject facts — it hallucinates them back. 3. Behavior gap → prompt engineering first: instructions + 3–5 few-shot examples; iterate against an eval set. 4. Fine-tune only when: prompting plateaued on a measured eval, behavior is stable long-term, and you hold 500+ quality examples. 5. Before choosing, build the eval set — 50+ representative cases with graded expected outputs; every option is scored against it, not against vibes. 6. Ship with hallucination mitigation: grounding citations, "answer only from context" instruction, and an abstain path.
**Decision tree:** `Needs private/fresh facts? → RAG. Needs format/tone/procedure? → prompt + few-shot. Prompt plateaued + 500+ examples + stable task? → fine-tune. Latency/cost bound with fixed narrow task? → fine-tune small model. Else → prompt.`
**Variation:** RAG blamed when retrieval is the failure — the model is fine but top-k returns wrong chunks. Eval retrieval (hit-rate of gold chunk in top-k) separately from generation before touching the model or prompt.

## 6. Hyperparameter optimization without overfitting the validation set
**Trigger:** Model chosen and honest pipeline confirmed; squeezing final performance; or val score climbs across trials while test score doesn't.
**Approach:** 1. Freeze the pipeline first — HPO on a leaky or shifting pipeline optimizes noise. 2. Define the search space from priors: for GBTs tune learning_rate, depth/leaves, min_child_samples, subsample, regularization; leave defaults elsewhere. 3. Use Optuna (TPE) with a pruner; budget 50–200 trials; log every trial. 4. Score trials with temporal CV (rolling-origin) for time-series, k-fold grouped by entity otherwise — never a single split. 5. Hold out a final untouched test set; evaluate the winner ONCE. 6. If best-trial val score exceeds test score by more than fold-level noise, you overfit the search — shrink the space and reduce trials.
**Checklist:** [ ] Pipeline frozen and leak-checked before HPO [ ] Search space listed with bounds and rationale [ ] CV scheme matches data dependence (temporal/grouped) [ ] Trial log persisted [ ] Test set touched exactly once [ ] Val-test gap within CV std [ ] Winning config committed with seed.
**Variation:** Thousand-trial fishing — with enough trials the val set is memorized through the search itself. The trial count is a hyperparameter of honesty: more trials demand a stricter final holdout.
